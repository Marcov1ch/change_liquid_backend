# Доменная модель и бизнес-логика

Справочник по предметной области: статусы, компоненты, интервалы, уведомления и правила создания замен.
Источник правды — код; здесь собраны правила, которые неочевидны из имён полей.

## Статусы замен

Перечисление `StatusEnum` (`src/app/common/enums.py`): `good`, `warning`, `critical`, `overdue`, `replaced`, `unknown`.

### Расчёт по пробегу

`StatusCalculator.calculate_status` (`src/app/common/utils/calculator.py`):

```
next_replacement_km = km_at_replacement + interval_km
km_remaining        = next_replacement_km - current_km
```

| Условие (`km_remaining`) | Статус |
|---|---|
| `< 0` | `overdue` |
| `0 … 250` | `critical` |
| `251 … 500` | `warning` |
| `> 500` | `good` |

Пороги заданы константами `_CRITICAL_KM = 250`, `_WARNING_KM = 500` в `calculator.py`.
Важно: `km_remaining == 0` — это `critical`, а не `overdue` (просрочка строго `< 0`).

### Расчёт по дате

`StatusCalculator.calculate_date_status` — используется для date-based компонентов (шины, страховка, аренда машиноместа):

| Условие (`days_remaining = next_change_date - today`) | Статус |
|---|---|
| `next_change_date is None` | `unknown` |
| `< 0` | `overdue` |
| `0 … warning_days` | `warning` |
| `> warning_days` | `good` |

`warning_days` берётся из `get_date_warning_days()` (`src/app/common/constants.py`): для `parking_monthly` — 1 день, для остальных date-based — 5.

### `replaced`

Проставляется **не** калькулятором, а хэндлером (`src/app/api/replacement/handler.py`, `_to_response`).
Для каждого компонента «живой» статус (`good/warning/critical/overdue`) имеет только **последняя** замена
(`get_latest_replacement_ids`). Все более старые записи того же компонента возвращаются со статусом `replaced`.

### Общий статус автомобиля

`StatusCalculator.get_vehicle_status` — берётся **худший** статус среди последних замен по каждому типу:

1. Нет замен вообще → `unknown`.
2. Для date-based компонентов (`tire_change`, `insurance`, `parking_monthly`) статус считается по дате, для остальных — по пробегу (интервал из настроек авто).
3. Приоритет: `overdue` > `critical` > `warning` > `good`.
4. Если у компонента не задан интервал — компонент пропускается.
5. Если ни один компонент не `overdue/critical`, но есть `warning` → статус авто `warning`, иначе `good`.

## Компоненты и интервалы

Список и значения по умолчанию — `COMPONENTS_CONFIG` (`src/app/common/component_config.py`),
доступен из API: `GET /api/v1/enums/component-configs`.

| Тип (`component_type`) | Название | Интервал, км | Интервал, мес |
|---|---|---|---|
| `engine_oil` | Моторное масло | 7000 | 12 |
| `transmission_oil` | Масло АКПП | 60000 | 60 |
| `brake_fluid` | Тормозная жидкость | 40000 | 24 |
| `coolant` | Антифриз | 60000 | 24 |
| `power_steering_fluid` | Жидкость ГУР | 40000 | 60 |
| `differential_oil` | Масло в редукторе | 50000 | 60 |
| `cabin_filter` | Фильтр салона | 15000 | 12 |
| `spark_plugs` | Свечи зажигания | 45000 | 24 |
| `air_filter` | Воздушный фильтр | 10000 | 12 |
| `fuel_filter` | Топливный фильтр | 50000 | 24 |
| `tire_change` | Замена шин | — | — (только по дате) |
| `insurance` | Страховка | — | — (только по дате) |
| `parking_monthly` | Аренда машиноместа | — | — (только по дате) |

- У **всех** компонентов, кроме date-based (`tire_change`, `insurance`, `parking_monthly`), есть **оба** интервала: по пробегу и по месяцам.
- `tire_change` — особый тип: его нет в `COMPONENTS_CONFIG`, у него нет интервалов по км/мес. Дата следующей замены (`next_change_date`) задаётся вручную при создании записи, статус считается только по дате. Пробег установки сохраняется в `km_at_replacement`; в ответе отдаётся `km_traveled` — сколько км проехали шины (до следующей записи шин или до текущего пробега авто для последней записи). Уведомлений по пробегу для шин нет.
- `insurance` — особый тип, также вне `COMPONENTS_CONFIG`, только по дате. При создании `next_change_date` обязательна; `km_at_replacement` и `interval_km` сохраняются как `0`, `work_price` — `None`, стоимость страховки — в `component_price`. В ответе `next_replacement_km`, `km_remaining` и `km_traveled` — `null`. Уведомления по пробегу для страховки нет.
- `parking_monthly` — аренда машиноместа, вне `COMPONENTS_CONFIG`, только по дате. `replacement_date` — начало аренды, `next_change_date` — окончание и обязательна; `km_at_replacement` и `interval_km` сохраняются как `0`, `work_price` — `None`, стоимость — в `component_price`, место/номер договора — в `component_name`. В ответе `next_replacement_km`, `km_remaining` и `km_traveled` — `null`. Уведомление приходит за 1 день до окончания; в день окончания статус `warning`, `overdue` — со следующего дня.
- Интервал по пробегу влияет на статус (`good/warning/...`), интервал по месяцам — на `next_change_date` / `days_remaining`.
- Интервалы хранятся у автомобиля (колонки `*_interval_km` / `*_interval_months`). Если значение не задано — подставляется дефолт из `COMPONENTS_CONFIG` (см. `VehicleRepository._intervals_and_flags`).
- Флаги уведомлений также хранятся у автомобиля (`*_notify_enabled`, плюс `tire_notify_enabled`, `insurance_notify_enabled` и `parking_monthly_notify_enabled`) и переключаются через `PATCH /api/v1/vehicles/{id}/notify`.

## Прочие траты

Прочие траты (`other_expenses`) — универсальные записи о расходах на автомобиль: штраф, мойка, почасовая парковка и т.п. Поля: `name` (свободное название, до 100 символов), `expense_date` (не позже сегодняшнего дня), `amount` (строго больше `0`, целые рубли).

- Это **не** обслуживание и **не** компонент замены: прочие траты не входят в `ComponentType`, не создают `ReplacementDB`, не влияют на статусы, пробег, интервалы и уведомления.
- Дубли разрешены: две траты с одинаковыми названием и датой допустимы.
- Чтение разрешено и для архивного автомобиля; создание/редактирование/удаление — только для активного.
- Прочие траты входят в публичную историю и увеличивают общий итог расходов (вместе со стоимостью замен и работ). Аренда машиноместа — отдельный date-based компонент `parking_monthly`; почасовая парковка — только прочая трата.
- При полном (hard) удалении автомобиля его прочие траты удаляются.

## Ремонты и обслуживание

Ремонт (`repairs`) — запись о работах: дата, обязательный пробег (`km_at_repair >= 0`), опциональное описание, обязательная стоимость работ (`work_cost >= 0`) и обязательная стоимость запчастей (`parts_cost >= 0`). Если работы или запчасти не оплачивались, передаётся `0`. В ремонт можно включить только **km-based** компоненты из `COMPONENTS_CONFIG`; шины, страховка и аренда машиноместа в ремонтах не участвуют.

- Для каждого выбранного km-based компонента автоматически создаётся служебная замена (`component_name = "ВНЕСИТЕ ИЗМЕНЕНИЕ"`, цены `0`, дата и пробег ремонта, `source_repair_id`).
- Стоимость ремонта учитывается один раз в `work_cost` + `parts_cost`; служебные замены имеют нулевую стоимость, поэтому задвоения нет.
- Нетронутые служебные замены синхронизируются при изменении ремонта (дата, пробег, состав компонентов). Изменённые пользователем карточки не трогаются; вручную удалённая служебная замена не восстанавливается.
- Пока ремонт содержит компонент на дату, замена этого компонента на ту же дату не может иметь положительную стоимость (`component_price`/`work_price`). Проверка действует при создании, обновлении и bulk-создании замен, а также при создании/обновлении ремонта.
- Обновление ремонта — полное (`PUT`): можно изменить описание, стоимости работ/запчастей и состав компонентов.
- При создании/обновлении ремонта уведомления не запускаются; служебные замены участвуют в обычном трекинге и статусах.
- Пробег автомобиля обновляется только вверх.
- При удалении ремонта нетронутые служебные замены удаляются, изменённые — остаются с очищенным `source_repair_id`.
- Ремонты входят в публичную историю и общий итог расходов; их стоимость не включает прочие траты.

## Заправки

Заправка (`fuel_records`) — независимая запись о топливе: дата (`fuel_date`), пробег (`km_at_fuel >= 0`), объём (`liters > 0`, допускаются дробные значения) и стоимость (`total_cost >= 0`). Все поля обязательны; дата не может быть в будущем; дубли разрешены.

- Заправки не являются компонентом замены, ремонтом или прочей тратой; не влияют на статусы и уведомления.
- Если пробег заправки больше текущего пробега авто — `current_km` увеличивается; уменьшение и удаление записей пробег авто не снижает.
- Расход `л/100 км` вычисляется динамически между соседними заправками по возрастанию пробега: `liters / (km - previous_km) * 100`. Для первой записи или при разнице пробега `<= 0` расход не определяется (`null`). В БД расход не хранится.
- Чтение разрешено и для архивного автомобиля; создание/редактирование/удаление — только для активного.
- Заправки входят в публичную историю и общий итог расходов.
- При полном (hard) удалении автомобиля его заправки удаляются.

## Статистика расходов

Статистика по месяцам и годам рассчитывается на frontend из уже загруженных записей автомобиля: замен, ремонтов, заправок и прочих трат. Отдельного backend-эндпоинта и хранения нет.

- Замены: `component_price + work_price`.
- Ремонты: `work_cost + parts_cost`.
- Заправки: `total_cost`.
- Прочие траты: `amount`.
- Месяц определяется по дате записи (`replacement_date`, `repair_date`, `fuel_date`, `expense_date`) без пересчёта часовых поясов.
- Служебные замены ремонтов имеют нулевую стоимость, поэтому не задваивают суммы ремонтов.
- Доступные годы — все годы, в которых есть записи, плюс текущий год.
- Статистика доступна как в кабинете, так и на публичной странице; публично показываются только агрегаты по уже открытым данным.

## Уведомления

Уведомления отправляются только пользователям с подтверждённым email (`users.email_verified = true`). Неподтверждённые пользователи могут пользоваться приложением, но письма (включая восстановление пароля и уведомления о заменах) не отправляются.

Письмо подтверждения отправляется при регистрации и смене email. Повторная отправка (`POST /auth/resend-verification`) ограничена кулдауном 60 секунд: при досрочном запросе возвращается `429` с заголовком `Retry-After`.

Уведомления делятся на два независимых механизма.

### 1. По дате (по месяцам) — планировщик

`src/app/services/scheduler.py`, APScheduler `BackgroundScheduler`, cron **ежедневно в 09:00** (`hour=9, minute=0`).

Алгоритм `_check_date_notifications`:
1. Берёт все активные автомобили, для каждого — настраиваемые компоненты + date-based (`tire_change`, `insurance`, `parking_monthly`).
2. Пропускает компонент, если его уведомления выключены (`notify_flags`), а также весь автомобиль, если email владельца не подтверждён.
3. Ищет последнюю замену и вычисляет `next_change_date`:
   - date-based (шины, страховка, аренда машиноместа) — сохранённая дата `next_change_date`;
   - остальные — `replacement_date + interval_months` (функция `add_months` с учётом переполнения дней, напр. 31.01 + 1 мес → 28.02).
4. `days_remaining = next_change_date - today`:
   - `< 0` → `overdue`, но только если ещё не слали (`date_overdue_notified`);
   - `0 … warning_days` → `warning`, только если не слали (`date_warning_notified`); `warning_days` = 1 для `parking_monthly`, 5 для остальных;
   - больше `warning_days` → флаги сбрасываются (уведомление «перевзводится» на следующий цикл).
5. Отправляет письмо (`send_date_notification_email`) и фиксирует флаг отправки.

Это единственный механизм, который шлёт письма **автоматически по расписанию**.

### 2. По пробегу — по событию

`src/app/services/notification_service.py`, вызывается через `BackgroundTasks` после:
- создания/обновления замен,
- обновления пробега авто (`PATCH /vehicles/{id}/km`, `PATCH /vehicles/{id}`).

`check_vehicle_notifications` группирует все «тревожные» компоненты авто в **одно** письмо (`send_grouped_notification_email`). Если email владельца не подтверждён, письмо не отправляется, а флаги отправки для отложенных уведомлений не обновляются (уведомление будет отправлено после подтверждения). Флаги `good` при этом сбрасываются как обычно.

Логика по статусу компонента:
- `good` → флаги сбрасываются;
- `warning` → письмо один раз (флаг `warning_notified`);
- `critical` → письмо один раз (флаг `critical_notified`);
- `overdue` → повторное уведомление каждые `RE_NOTIFY_KM = 500` км (порог = последний уведомлённый пробег либо `next_replacement_km`, плюс 500; хранится в `overdue_notified_at_km`).

Флаги — колонки `ReplacementDB`: `warning_notified`, `critical_notified`, `overdue_notified_at_km`, `date_warning_notified`, `date_overdue_notified`.

## Создание замен и проверка хронологии

`src/app/services/replacement_service.py`, метод `create`.

Валидация для компонентов **не** date-based:
- `km_at_replacement >= 0`, `replacement_date <= сегодня`;
- **хронология** — пробег и дата новой замены не меньше, чем у предыдущей замены того же компонента (`_validate_sequence`, `get_last_replacement`);
- **нет дубликата** — для этого компонента ещё нет замены с таким же `km_at_replacement`;
- если новый пробег больше текущего пробега авто — `current_km` авто обновляется.

Для date-based (`tire_change`, `insurance`, `parking_monthly`) проверки хронологии и дубликата пропускаются (можно задавать `next_change_date` вручную). Для шин введённый пробег установки сохраняется, и `current_km` авто обновляется, если он больше текущего. Для страховки и аренды машиноместа `next_change_date` обязательна, пробег и работы не сохраняются (`0`/`None`); для парковки также проверяется, что дата окончания не раньше даты начала аренды.

При **обновлении** (`update`) те же проверки выполняются с `exclude_id` и поиском соседей (`find_neighbors`): значение не должно быть меньше предыдущей и больше следующей замены. При изменении даты не-date-based замены пересчитывается `next_change_date` и сбрасываются date-флаги; для date-based при смене `next_change_date`, а для date-only также при смене даты начала сбрасываются date-флаги.

### Массовое создание (ТО)

`POST /api/v1/vehicles/{id}/replacements/bulk` (`ReplacementsBulkRequest`), `1…10` замен за раз.
- Все замены создаются в одной транзакции (`commit=False`, затем один `db.commit()`).
- Любая ошибка валидации (`ValueError`) → `db.rollback()` и HTTP 400 (атомарно: либо всё, либо ничего).
- После успешного коммита запускается проверка уведомлений по пробегу.

## `Vehicle` и `VehicleSize`

- **`Vehicle`** (`VehicleDB`) — основной автомобиль: марка/модель (ссылки на `brands`/`models`), госномер, год, `current_km`, интервалы и флаги уведомлений по компонентам. Справочные данные марки/модели сидируются (`seed_brands`). Госномер не уникален: разные пользователи могут вести историю одного автомобиля. Формат свободный (поддерживаются европейские и другие номера) до 15 символов, без управляющих символов; по краям обрезается, приводится к верхнему регистру, пробелы и дефисы внутри сохраняются.
- **`VehicleSize`** (`VehicleSizeDB`) — **справочник допустимых дисков и шин** для авто (появился в 2026.18.0). Это «что подходит машине», а не история фактических замен.
  - `kind = 'rim'`: `diameter`, `pcd`, `et_from`/`et_to`, `width_from`/`width_to`.
  - `kind = 'tire'`: `size`, `label`.
  - Связан с авто через `vehicle_id` (`ondelete CASCADE`); обновляется целиком через `PATCH /api/v1/vehicles/{id}/sizes` (`replace_sizes` — полная замена списков).
- **Фактическая** замена шин — это запись `Replacement` с `component_type = tire_change` и `next_change_date`. Не путать со справочником `VehicleSize`.
