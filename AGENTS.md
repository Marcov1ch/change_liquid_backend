# AGENTS.md

## Команды разработки

### Основные
- `poetry install` — установка зависимостей
- `make run` — запуск dev-сервера (`PYTHONPATH=src poetry run python src/app/main.py`). Приложение доступно на http://localhost:8000, Swagger — на http://localhost:8000/docs
- `make test` — запуск тестов (`PYTHONPATH=src poetry run pytest src/tests -v`). При прямом запуске pytest всегда задавайте `PYTHONPATH=src`
- `make lint` — проверка стиля (flake8, лимит 110 символов, см. setup.cfg)
- `make mypy` — проверка типов (mypy)
- `make ruff` — проверка через ruff (`poetry run ruff check src`)
- `make radon` — анализ сложности кода: только проблемные блоки C-F и средняя сложность по всему коду (`poetry run radon cc src -s --total-average -n C`)
- `make check` — `lint + mypy + test` одной командой (проверка перед сдачей работы)
- `make clean` — очистка кэшей (`__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`)

### Проверка перед сдачей работы
- В CI гоняются `flake8`, `mypy`, `pytest` (запускаются параллельно). Зависимости в CI ставятся `poetry install --no-root` (без установки текущего пакета). `ruff` в CI **не** используется.
- Локально то же самое одной командой: `make check` (= `make lint && make mypy && make test`).
- `make ruff` — опциональная локальная проверка. Можно прогнать её дополнительно, но минимум — `make check`.
- Деплой в `master` возможен только при успешном прохождении всех трёх проверок из CI.

### Важные нюансы
- Тесты лежат в `src/tests/` (мн.ч.). В `setup.cfg` есть `exclude = src/test` (ед.ч.) — это не ошибка, просто особенность конфига.
- Конфиг flake8 содержит `per-file-ignores` для нескольких файлов с длинными строками.
- Для mypy включён `disallow_untyped_defs` и `check_untyped_defs` — при правках следуйте существующему стилю типизации.
- В `src/tests/conftest.py` принудительно задаётся `SECRET_KEY` для тестов.

## Структура репозитория (верхний уровень)
Короткий ориентир по ключевым директориям:
- `src/app/api/` — хендлеры, роуты, схемы API
- `src/app/auth/` — авторизация, JWT, работа с паролями
- `src/app/common/` — общие утилиты, конфиги, middleware, enums
- `src/app/db/` — модели, миграции-хелпер, сидирование, подключение к БД
- `src/app/repository/` — слой доступа к БД

- `src/tests/` — тесты
- `alembic/` — миграции Alembic и конфиг
- `data/` — локальная SQLite БД (не коммитится)
- `.github/workflows/` — CI-конфиг

## Архитектура

### Доменная логика
- Статусы (`good/warning/critical/overdue/replaced`), компоненты и интервалы (км/месяцы), работа планировщика (09:00) и уведомлений по пробегу, проверка хронологии и bulk-создание (ТО), отличие `Vehicle` от `VehicleSize` — в **[DOMAIN.md](DOMAIN.md)**. Это ключевой справочник по предметной области, обязательно сверяйтесь с ним перед правкой расчётов и уведомлений.

### Точки входа
- `src/app/main.py` — точка входа FastAPI. При старте: загружает `.env`, настраивает логирование, запускает миграции, инициализирует БД (сидирование), монтирует роутеры, стартует планировщик уведомлений.
- `src/app/api/routes.py` — регистрация v1-роутов (`/api/v1/*`).
- `app.auth.handler.router` монтируется напрямую в `main.py`. Auth-логика также реализована в `src/app/auth/` (JWT, обработчики, схемы).

### База данных
- SQLAlchemy 2 + SQLite. Путь к БД берётся из `DB_PATH` (по умолчанию `data/app.db`). `engine` использует `connect_args={"check_same_thread": False}`.
- Миграции Alembic: `alembic/`, `alembic.ini`. `alembic/env.py` добавляет `src` в `sys.path` и использует `app.db.models.Base.metadata`.
- Кастомный механизм миграций: `src/app/db/migrate.py`. Если БД пустая (нет таблиц) — `Base.metadata.create_all()` + `alembic stamp head`. Если есть таблицы — `alembic upgrade head`. **Не меняйте** это поведение без понимания.
- Инициализация/сидирование: `src/app/db/database.init_db()` вызывает `seed_brands()`. Схема управляется миграциями.
- Модели: `src/app/db/models.py` (User, Vehicle с интервалами/флагами уведомлений по компонентам, VehicleSize, Replacement с флагами уведомлений, Brand, Model).

### Прочее
- Сервисный слой: `src/app/services/` (включая планировщик `scheduler.py` и уведомления по email).
- Репозитории: `src/app/repository/`.
- Общие утилиты/конфиги: `src/app/common/`.
- Авторизация: `src/app/auth/` — JWT, обработчики, схемы.

## Связь с фронтендом

Этот бэкенд работает в паре с фронтендом: `../change_liquid_frontend` (рядом в одном workspace).

- **Контракт API** — OpenAPI, генерируемый FastAPI. Доступен при запущенном бэке: `http://localhost:8000/openapi.json`, Swagger UI: `http://localhost:8000/docs`.
- **Синхронизация**. При любом изменении API сверяйтесь с фронтом. Если фронт использует типы/эндпоинты из OpenAPI — при правках бэка учитывайте влияние на клиент.
- **Обратная совместимость**. Старайтесь не ломать существующий контракт. Добавляйте новые поля/эндпоинты, не удаляйте и не переименовывайте публичные поля/пути без веской причины.
- **Breaking changes**. Если изменение всё же ломающие — **обязательно** согласуйте с фронтендом и синхронизируйте изменения в обоих репозиториях. При таких изменениях отразите суть в `CHANGELOG.md` (ориентируйтесь на существующий стиль файла).
- **Где хранить openapi**. В этом репозитории **нет** статичного `openapi.yaml`. Единый источник правды — живой `openapi.json` от запущенного FastAPI-приложения.

## Коммиты и Pull Request

- **Коммиты и PR**: выполняются только пользователем. **Никогда** не выполняйте `git commit`, `git push`, `git add` (включая с коммит-сообщением), `git merge`, `git rebase` и прочие git-действия, приводящие к созданию коммитов или пушу (см. также «Строгие запреты»).
- **Перед тем как считать задачу выполненной**: убедитесь, что код проходит `make check` (lint + mypy + test). При желании добавьте `make ruff`. Подробнее см. раздел «Проверка перед сдачей работы».
- **API-изменения**: при изменении API учитывайте влияние на фронтенд (`../change_liquid_frontend`). Если изменения ломают обратную совместимость — обязательно согласуйте их с фронтендом и отразите суть в `CHANGELOG.md`.

## Конфигурация и окружение

- Переменные окружения берутся из `.env` (см. `.env.example`). Обязательные: `SECRET_KEY`. Опциональные: `DB_PATH`, `SMTP_HOST/PORT/USER/PASSWORD/FROM`, `FRONTEND_URL`.
- Email-уведомления и планировщик (APScheduler) стартуют при запуске приложения.
- `data/app.db` хранится в `data/`. Директория `data/` и файлы `*.db`/`*.sqlite*` игнорируются git (`.gitignore`). **Никогда** не коммитьте локальную БД.

## Строгие запреты

- **Миграции**: не редактируйте уже применённые файлы миграций в `alembic/versions/`. Новые изменения схемы — только через новую миграцию (`alembic revision --autogenerate`).
- **Alembic**: не трогайте `alembic stamp` вручную.
- **Миграционный механизм**: не меняйте поведение `src/app/db/migrate.py` без полного понимания его логики (особенность: пустая БД → create_all + stamp head).
- **Схема**: при изменении БД обновляйте **именно** Alembic-миграции, а не только модели.
- **Секреты**: не коммитьте `.env`, ключи, пароли, токены.
- **БД-файлы**: не коммитьте `data/app.db` и любые локальные SQLite-файлы.
- **Комментарии**: не добавляйте комментарии в код без явного запроса.
- **Git**: см. раздел «Коммиты и Pull Request».

## Советы при работе

- Всегда используйте `PYTHONPATH=src` при запуске pytest из корня репозитория.
- Учитывайте side-эффекты при импорте `src/app/main.py` (миграции, сидирование, старт планировщика) — это важно при тестировании/импорте.
- Перед тем как считать задачу выполненной, обязательно убедитесь, что код проходит минимально необходимый набор проверок (см. раздел «Проверка перед сдачей работы»).
- При изменении поведения в домене — обновите `DOMAIN.md`. Если док расходится с кодом — верьте коду, но отметьте расхождение и предложите правку.
- Держите изменения минимальными и проверяемыми. Если не уверены — лучше спросить.
